# UpRiver UI redesign: research brief

**Summary:** Redesign UpRiver's vanilla-JS UI as a modernized, Jenkins-familiar CI/CD console (sidebar, numbered build history with status balls, stage grid, breadcrumbs, console log) with the Build page as the priority screen, in light and dark themes that follow the OS.

- **Date:** 2026-10-13
- **Status:** confirmed (key questions answered directly by the user)
- **Open questions:**
  1. Visual identity: mark and palette are to be invented (name suggests flow / water / upstream). Needs a decision in planning.
  2. Compare runs: no API endpoint exists. Client-side diff of two builds' snapshots (params, files, stage results) is feasible; confirm that is enough.
  3. Run-config editing: is a structured params/stages editor enough, or should admins keep raw JSON as an "advanced" fallback?
  4. Log search, timestamps and line numbers: the API returns raw text (no per-line times). Client-side line numbers and search are fine; real timestamps need a backend change. Decide if out of scope.

## Product and jobs to be done

UpRiver is a small-team, Jenkins-inspired CI/CD tool: upload files into a pipeline's file set, run ordered stages (BVT/FVT/smoke/regression) as shell commands, read logs, download artifacts. FastAPI backend, static UI served from `upriver/static/` (`index.html`, `app.js`), hash routes `#/`, `#/p/{id}`, `#/b/{id}`.

Jobs:
- Upload new files to a pipeline's file set (optionally extract zips), see what changed.
- Pick or save a run configuration (params + enabled stages), optionally pin older file versions.
- Trigger a build and watch stages and live logs.
- When something fails: find the failing stage fast, read its log, abort if needed, download artifacts.
- Compare runs ("what changed between #11 (green) and #12 (red)?").
- Admin: create pipelines and edit pipeline JSON config.

## Audience and context

Small engineering team, shared tokens, no per-user roles. Desktop primary (wide monitor, often next to a terminal), but must be usable at narrow widths (phone check of a running build). Visits are task-driven and frequent; most time is spent on the Build page, often when a build has failed. Users already know Jenkins.

## Feel and mood (made actionable)

"Jenkins-familiar but modern" means concretely:
- **Keep the vocabulary:** left sidebar of per-context actions (pipeline: Build now, Files, Configs, Settings; build: Console, Artifacts, Abort, Compare), breadcrumb trail `Dashboard > pipeline > #12`, numbered builds ("#12") with a status ball, stage view as columns/cells, "Console Output" as a dark monospace panel.
- **Drop the 2009 chrome:** no gradients, no bevels, no tiny 11px grey text, no table-of-links-only pages. Use flat surfaces, 1px hairline borders, 6-8px radii, one accent, generous hit targets (min 32px) but compact vertical rhythm.
- **Dense, not airy:** many builds and stages visible without scrolling; rows ~36px, 13-14px body text, tabular numerals for durations and numbers.
- **Status is the loudest thing on screen:** colored status balls/icons (passed green, failed red, running blue with subtle pulse, aborted orange, queued/pending/skipped grey) always paired with an icon shape and text, never color alone.
- **Calm, utilitarian tone:** short plain labels, no marketing copy, no emoji. Motion limited to the running pulse and log follow; respect `prefers-reduced-motion`.
- **Themes:** follow OS via `prefers-color-scheme`; both themes designed, not inverted. Log panel is dark in both themes (or theme-matched with equal contrast).
- **Type:** system font stack for UI, `ui-monospace` stack for logs, ids, paths, params. No webfonts.

## References (borrow / avoid)

Sourced from existing knowledge, not live browsing.
- **Jenkins classic job page + Stage View:** borrow the left action sidebar, build history list with #number + ball + timestamp, and the stage-by-column grid with per-stage duration. Avoid the cramped table density, hidden actions and heavy page reloads.
- **Jenkins Blue Ocean:** borrow the horizontal pipeline graph of stage nodes with status icons, failed stage auto-focused with its log opened below. Avoid the huge whitespace and the single-purpose full-screen views.
- **GitHub Actions run page:** borrow the job/step list left with a log pane right, collapsible steps, per-step duration, line numbers, in-log search, "scroll to bottom"/follow behavior, re-run affordance. Avoid hiding the failure behind collapsed groups.
- **GitLab pipeline graph:** borrow the clear left-to-right stages with job pills and a status icon shape per state, and the retry/cancel affordances on the node. Avoid its dependency-line complexity (UpRiver stages are a linear list).

## Page inventory

| Page | Route | Job |
|---|---|---|
| Sign-in bar | all | Set name, team token, optional admin token (localStorage); forced on first visit. Should become a user menu / first-run screen. |
| Dashboard | `#/` | Scan all pipelines and their last-build status at a glance; open one; admin creates a pipeline. |
| Pipeline | `#/p/{id}` | Hub: file set (upload, extract zips, per-path history, pin version, download, remove), Run panel (config dropdown, params, stage checkboxes, Build now, Save as config, Delete config), build history, admin Settings JSON. |
| Build | `#/b/{id}` | Priority. Header (status, number, by, config, params, files, duration), Abort, stage list with status/duration/exit code, live log per stage (offset poll 1.5 s, build poll 2 s), auto-follow of running then failed stage, artifacts download. |
| Compare (new) | e.g. `#/c/{a}/{b}` | Side-by-side params, files@version, stage statuses/durations of two builds. Uses existing build snapshot data. |

API usage that must be preserved: pipelines list/create/get/update, configs list/upsert/delete, files list/history/upload/remove/download, build trigger (`config_id`, `params`, `stages`, `upload_ids`), builds list/get, stage log with `offset`, abort, artifacts list/download (fetch to blob, token never in URL).

## Current UI pain points

1. **JSON textareas** for New pipeline and Settings: error-prone, no validation hints, and a saved change needs a manual reload ("reload the page to see new params and stages").
2. **No sidebar or contextual actions;** the build page has no clear primary action or navigation between builds (previous/next build, back to pipeline history).
3. **Breadcrumbs are minimal text** ("Pipelines / name / #n"); no pipeline name on the dashboard row context, no build number in the page title.
4. **Status discoverability:** text pills only, no shapes; no failing-stage summary on the history list; no sparkline/trend of recent builds on the dashboard; last build only.
5. **Stages as a vertical button list,** no stage-view grid across builds; failed stage is not visually dominant; skipped/pending stages are indistinguishable at a glance.
6. **Log usability:** no line numbers, no follow toggle (only implicit "stay at bottom"), no search, no copy/download of the log, no timestamps, no ANSI handling, hard `max-height: 28rem` box, no "jump to first error", no full-height mode.
7. **Upload feedback:** no drag and drop, no progress, no per-file result list, result is a one-line count message that disappears on next action; no diff of what changed.
8. **Run panel is a long form:** config, params, stages and pins live far apart; pinned versions are invisible except a "n pinned" count; unsaved changes vs saved config are unclear.
9. **Empty states** are bare muted sentences ("No files yet.", "No builds yet.") with no next step.
10. **Errors** appear as unstyled red text at the end of a section; destructive actions (Remove, Delete config, Abort) have no confirmation or undo.
11. **Sign-in:** three raw fields permanently in the header; no sign-out; admin vs team capability not shown (admin sections are visible to everyone and fail with 403).
12. **No compare view,** no re-run with same config, no build search/filter, history capped at 50 with no paging.
13. **Responsive:** tables scroll horizontally; the sign-in bar crowds narrow screens; touch targets are small.
14. **Accessibility gaps:** color-only status in places, no focus styles beyond defaults, no skip link, live log not announced politely.

## Constraints

- Vanilla HTML/CSS/JS, no frameworks, no npm or build step; files stay in `upriver/static/` and are served as-is.
- No external CDNs, fonts or icon sets at runtime; system font stacks; icons as inline SVG or CSS shapes.
- All untrusted text (logs, names, params, paths, descriptions) through `textContent` / the `el()` helper, never `innerHTML`; ANSI rendering must build DOM nodes.
- Keep all current functionality and API contracts; no breaking backend changes (additive endpoints only, if any).
- Hash routing retained (`#/`, `#/p/{id}`, `#/b/{id}`); new routes additive.
- Pollers stop when their node leaves the document; keep that pattern.
- Light and dark first-class via `prefers-color-scheme`; WCAG AA contrast for text and status colors in both.
- Works from ~360px up to wide desktop; keyboard operable; `prefers-reduced-motion` respected.
- Test hook: `test_index_served` must keep passing; manual checklist in `docs/plan.md` Phase 4 still applies (including `<img onerror>` in a log rendering as text).

## Taste signals

- **Jenkins vocabulary stays:** sidebar, breadcrumbs, `#N` build numbers, status balls, Stage View grid, "Console Output".
- **Status balls:** round indicator with a distinct glyph per state (check, cross, spinner/pulse, dash, stop), consistent everywhere a status appears.
- **OS theme:** follow `prefers-color-scheme`, no manual toggle required; both themes polished.
- **Build page first:** stage pipeline view on top, live log dominating the rest, failure is the focal point; other pages inherit its styling.
- **Dense, not airy:** compact rows, small-but-legible type, information over decoration.
- **Self-contained and plain:** system fonts, inline SVG, no dependencies; modernized, not trendy (no glassmorphism, no illustrations).
- **Brand direction (to invent):** a simple mark suggesting an upward flow or river bend; restrained palette led by a cool blue/teal accent so the status colors keep their meaning.
